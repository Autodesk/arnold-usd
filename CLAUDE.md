This file provides the context an AI assistant needs to work effectively on this

## Project overview

**arnold-usd** is Autodesk's integration of the Arnold renderer with Pixar USD
and the Hydra rendering framework. It lets Arnold render USD scenes and exposes
Arnold as a Hydra render delegate, used in Houdini (Solaris/husk), Maya, and
any USD-based application.

Key external repositories to consult for reference:
- **OpenUSD** — https://github.com/PixarAnimationStudios/OpenUSD  
  The USD and Hydra core. `third_party/renderman/plugin/hdPrman` is the
  reference Hydra render delegate (Pixar's RenderMan). Use it as a benchmark
  for feature parity.
- **HoudiniUsdBridge** — https://github.com/sideeffects/HoudiniUsdBridge/tree/master/src/houdini  
  The bridge between Houdini (Solaris, husk) and USD/Hydra. Use it to
  understand what Houdini expects from a render delegate or procedural — both
  for Houdini-specific behavior and for general Hydra delegate support patterns.

## The three USD → Arnold code paths

This is the most important concept in the codebase. There are **three distinct
paths** by which a USD scene is converted to Arnold data. All three are
exercised by the testsuite.

### Path 1 — Direct USD translator (legacy)

**Location:** `libs/translator/reader/`  
**Activated by:** environment variable `PROCEDURAL_USE_HYDRA=OFF`  
**Status:** Deprecated. Will be removed in a future major version.

This path reads a USD stage directly using USD API calls, without going through
Hydra at all. It is the oldest path and is being phased out, but the testsuite
still exercises it to catch regressions.

When implementing a new feature, **try to implement it here too** so the
testsuite has full coverage. If it is genuinely too difficult (e.g., because the
feature depends on Hydra abstractions), it is acceptable to skip this path.

### Path 2 — Hydra 1 (ENABLE_SCENE_INDEX=OFF)

**Location:** `libs/render_delegate/`  
**Activated by:** building without `ENABLE_SCENE_INDEX` (the default).  
**Status:** The most widely deployed path. Used in:
- Arnold command-line rendering (kick)
- Most DCC plugins (current MtoA, HtoA, etc.)
- Older Houdini and Maya versions

Hydra drives the scene delegate; each USD prim type is translated by a
dedicated Sprim/Rprim/Bprim class in `libs/render_delegate/`. This path does
**not** use any scene-index plugins from `plugins/scene_index/`.

### Path 3 — Hydra 2 (ENABLE_SCENE_INDEX=ON)

**Location:** `libs/render_delegate/` (same classes, different code branches)
**+ `plugins/scene_index/`** (scene-index plugin pipeline)  
**Activated by:** building with `BUILD_SCENE_INDEX_PLUGIN=ON` or
`ENABLE_SCENE_INDEX_IN_BUNDLE=ON`, which defines `ENABLE_SCENE_INDEX=1`.  
**Status:** The future standard. Currently used in:
- Houdini 21 (Solaris / husk)
- Maya 2027

In this mode the Hydra 2 scene-index pipeline is inserted before the render
delegate. Scene-index plugins (SIPs) in `plugins/scene_index/` transform the
scene graph upstream so that the render delegate receives already-resolved data.
Code gated on `#ifdef ENABLE_SCENE_INDEX` lives in both the render delegate and
the SIP files.

---

## ⚠️ Critical implementation rule

> **Every bug fix and every new feature MUST be implemented in both Path 2
> (Hydra 1) and Path 3 (Hydra 2).**

Implementing a feature only in the scene-index plugins (Path 3) is never
sufficient on its own — the Hydra 1 path must work too.

If the feature is simple enough, also implement it in Path 1 (translator/reader)
so the testsuite covers all three modes. If Path 1 is too difficult (e.g., it
requires Hydra abstractions that don't exist there), skip it and document why.

**Practical implication:** When adding a new feature:
1. Check whether the Hydra 1 render delegate already handles it inline (e.g., in
   a `Sync()` method). If not, add it there.
2. Check whether a scene-index plugin is needed for the Hydra 2 path. If so,
   create one under `plugins/scene_index/`.
3. The two paths must produce the same rendered result.

## Hydra 2 scene-index plugin conventions

Each SIP lives in `plugins/scene_index/` as a pair `fooSIP.h` / `fooSIP.cpp`.

- Wrap the entire `.cpp` content in `#ifdef ENABLE_SCENE_INDEX … #endif`.
- Subclass `HdSingleInputFilteringSceneIndexBase` for filtering plugins.
- Self-register via `TF_REGISTRY_FUNCTION(TfType)` and
  `TF_REGISTRY_FUNCTION(HdSceneIndexPlugin)`.
- Pick an insertion phase that respects ordering relative to other SIPs
  (see existing phases in each SIP file).
- Register for renderer string `"Arnold"`.
- Add the plugin to `plugInfo.json.in`, `CMakeLists.txt`, and `SConscript`.

Reference pattern: look at `meshLightResolvingSIP.cpp` and
`extComputationPrimvarPruningSIP.cpp` for typical implementations.

## Build flags

Build with SCons (`SConstruct`) or CMake (`CMakeLists.txt`).

| Flag | Meaning |
|------|---------|
| `BUILD_RENDER_DELEGATE=ON` | Build the Hydra render delegate |
| `BUILD_SCENE_INDEX_PLUGIN=ON` | Build the scene-index plugin (enables Hydra 2) |
| `ENABLE_SCENE_INDEX_IN_BUNDLE=ON` | Enable Hydra 2 inside a bundled build |
| `BUILD_PROCEDURAL=ON` | Build the Arnold USD procedural |
| `BUILD_TESTSUITE=ON` | Build and install test infrastructure |
| `USD_BUILD_MODE` | `shared_libs` / `monolithic` / `static` — affects linking |
| `MTOA_BUILD=ON` | Enable MtoA-specific scene-index plugin (`mtoaSIP.cpp`) |
| `ARNOLD_PATH` | Path to Arnold SDK installation |
| `USD_PATH` | Path to USD installation |

When `BUILD_SCENE_INDEX_PLUGIN=ON` or `ENABLE_SCENE_INDEX_IN_BUNDLE=ON`, the
compiler flag `-DENABLE_SCENE_INDEX=1` is set, enabling all `#ifdef
ENABLE_SCENE_INDEX` blocks.

## Tests

Tests live in `testsuite/`. Each test is a numbered directory (`test_NNNN/`)
containing:
- `data/` — input USD files (`.usda`/`.usd`), Arnold scene files (`.ass`), etc.
- `ref/` — reference images for pixel-comparison.
- A short `README` describing what the test covers.

**Run a single test / generate its reference (preferred):**
```bash
abuild test_NNNN                      # build + run one test, compare against ref/
abuild test_NNNN UPDATE_REFERENCE=1   # run it and (re)generate ref/ from the output
```
Always use `abuild` for anything testsuite-related. Do **not** hand-render a
scene or hand-author a `ref/reference.tif` / `ref/README` claiming the reference
must be generated manually — `abuild … UPDATE_REFERENCE=1` renders the scene and
blesses the output as the reference. After creating or editing a
`testsuite/test_NNNN/` case, run `abuild test_NNNN UPDATE_REFERENCE=1` to produce
the reference, then `abuild test_NNNN` to confirm it passes.

**Run the whole suite:**
```bash
scons testsuite
```

The testsuite sets environment variables (`USD_PROCEDURAL_PATH`,
`PREFIX_TEST_RENDERDELEGATE`) and compares rendered output to reference images.

To exercise all three code paths, the testsuite runs each scene with:
- `PROCEDURAL_USE_HYDRA=OFF` (Path 1 — direct translator)
- Hydra 1 render delegate (Path 2)
- Hydra 2 render delegate with scene index (Path 3, when built)

## Code style

See `docs/conventions.md` and `docs/naming_conventions.md` for the full rules.
Key points:
- **C++**: clang-format 9.0.1; `#pragma once`; no `using namespace`.
- **Naming**: `HdArnoldFoo` for Hydra classes, `ArnoldFoo` for USD schema types,
  `str::foo` for `AtString` constants (defined in `libs/common/constant_strings.h`).
- **Arnold primvar namespace**: `primvars:arnold:*` passes Arnold attributes
  through to any prim.
- **USD schema names**: Arnold shader nodes use `info:id = "arnold:shader_name"`.

## Arnold SDK notes

The Arnold SDK (`ai_*.h` headers) must be installed at `ARNOLD_PATH`. These
headers are **not** included in this repository. When working without a local
Arnold installation:
- Runtime-guard new node types with `AiNodeEntryLookUp(str::node_name)`.
- Runtime-guard new parameters with `AiNodeEntryLookUpParameter(nentry, str::param)`.
- This ensures graceful degradation on older Arnold builds.

## Ongoing work context

The current development focus is bringing arnold-usd to feature parity with
hdPrman. A prioritised plan lives in the Claude plan file. Completed patches are
saved as `p*.patch` at the repo root. Patch naming: `p<phase>-<N>-<slug>.patch`.

When asked to implement the "next step" in the plan, read the plan file, check
which patches already exist, and implement the next uncompleted item.
